# pb

A protobuf module manager: modules and their versions resolved as
Go's are, every fetched artifact pinned and verified, lint and
breaking rules in CEL, code generated by plugins that run as OCI
images under a sandbox, and an editor served over the Language
Server Protocol. The contracts live under `docs/specs/`; this page is
the adopter's path through them.

## Install

```sh
task install          # builds ./cmd/pb into ~/.local/bin and installs shell completion
```

## From a buf project

`pb migrate` reads the buf configuration in the working directory (or
below it, `--config <dir>`) and writes pb's files beside it: a
workspace file, a module file per buf module, the lint file importing
the buf rules as a pb ruleset, the generation file, and the lockfile
the tidy at its end pins. It deletes no buf file. The module path of
the configuration's directory comes from the repository's `origin`
remote, or `--module`:

```
$ pb migrate --module example.com/weather
buf.yaml modules[0] proto -> proto/pb.yaml module: example.com/weather/proto
the lint file's rulesets github.com/greatliontech/buf-rules -> rulesets: path github.com/greatliontech/buf-rules version v0.2.0 alias buf (discovered)
buf.yaml.lint.use STANDARD -> enable: buf:STANDARD
buf.yaml.breaking.use FILE -> enable: buf:FILE
buf.gen.yaml plugins[0].local protoc-gen-go -> local: protoc-gen-go
buf.gen.yaml plugins[0].out gen -> out: gen
buf.gen.yaml plugins[0].opt paths=source_relative -> opt: paths=source_relative
proto/pb.yaml -> written
pb.work -> written
pb.lint.yaml -> written
pb.gen.yaml -> written
pb.lock -> written by the tidy
```

Every line is one fact of the buf configuration mapped to its pb
form; a fact pb has no form for is printed as `<key> !! <reason>` and
the verb exits 1 with the files written all the same. Then:

```
$ pb lint
$ pb build out.binpb
built 1 file(s) to out.binpb
$ pb dep verify
verified 1 cached module(s)
```

`pb lint` prints findings and exits 1 on an error-severity one; a
clean tree prints nothing. The buf rules are the ruleset
`github.com/greatliontech/buf-rules`, imported by the lint file under
the alias `buf` and pinned in `pb.lock` like any dependency.

### A migration that could not reach the ruleset

The migration reaches the network to discover the releases of the
buf dependencies it declares, the ruleset's release, a versionless
plugin's tags, and, in its tidy, to fetch what it pinned. A
dependency's release it cannot discover is an unmapped `!!` fact
naming the `--dep` flag; the ruleset's it reports the same way, and
writes the lint file's import without a version:

```
the lint file's rulesets github.com/greatliontech/buf-rules !! no version discovered (...): the import is written without a version; run `pb dep update github.com/greatliontech/buf-rules` over the written files once the ruleset can be reached, or pass --dep github.com/greatliontech/buf-rules=github.com/greatliontech/buf-rules@<version> to a fresh migration
```

The files on disk are the migration's; finish them in place. Fix the
reachability (the next section), then move the import to a release:

```
$ pb dep update github.com/greatliontech/buf-rules
pb.lint.yaml: github.com/greatliontech/buf-rules (no version) -> v0.2.0
```

A tidy that failed for the same reason is rerun with `pb dep tidy`
once the cause is fixed. A second `pb migrate` over the written files
is refused — the migration writes no file over one — so start over
only by removing what it wrote, and then the `--dep` flag pins the
version for a run that need not discover it.

## Reaching private origins

pb fetches modules itself; it does not use git's credential helpers.
Two routes:

- **HTTPS with a credential file.** A netrc file — `~/.netrc` by
  default, `_netrc` on Windows, or the one the `netrc` setting names
  (`PBNETRC`, or `netrc:` in the user configuration file) — with
  `machine <host> login <name> password <secret>` for each host. A
  credential goes to the host it names over HTTPS and nowhere else;
  the `default` entry is never lent to a host. Credentials never go
  in a project file.
- **SSH.** The `ssh` setting (`PBSSH`, or `ssh:` in the user
  configuration) lists comma-separated patterns in the `noproxy`
  grammar — a module path or a leading segment prefix of it,
  `corp.example.com` or `github.com/acme/*` — and a matching module
  is reached as `ssh://git@<host>/<path>`, authenticated through the
  running SSH agent alone, the host verified against your known
  hosts. No key file is read; a stale agent socket fails with its
  own message. The route changes nothing else: the module's identity,
  its pins and its provenance stay the HTTPS repository's, and a
  matching module still consults the source list — with a `proxy`
  configured, `noproxy` is what sends it to the origin.

The user configuration file is `pb/config.yaml` under the platform's
user configuration directory (`$XDG_CONFIG_HOME`, else `~/.config`,
on Unix); every key has an environment variable, `PB` and the key
upper-cased with its hyphen dropped (`netrc` is `PBNETRC`,
`plugin-pull` is `PBPLUGINPULL`). See `docs/specs/user-config.md` and
`docs/specs/module-resolution.md`.

## Generating with a host binary

Plugins are OCI images by default, pinned by digest and run in a
sandbox. A `local` entry in `pb.gen.yaml` runs a binary of the host
instead, outside every sandbox guarantee, so the root must say so in
its trust policy, `pb.trust.yaml`:

```yaml
execution:
  schemes:
    - local
```

Without it generation refuses the entry:

```
$ pb generate
pb: generate: the trust policy does not permit local-scheme plugins (plugin protoc-gen-go)
```

With it, the binary — found on `PATH` exactly as written, or
relative to the root where the command holds a path separator — runs
as the plugin process. Nothing of it is recorded in `pb.lock`: a host
binary has no identity pb could resolve, so none is claimed, and what
runs is what the command resolves to on each machine:

```
$ pb generate
protoc-gen-go: 1 file(s) into gen (runner native, tier Strong, bounds rlimits)
```

## The verbs

`pb dep` holds `init`, `tidy`, `download`, `update`, `verify`,
`graph` and `why`; `pb lint`, `pb breaking`, `pb build`, `pb export`,
`pb format` and `pb generate` work over the workspace; `pb plugin`
builds and publishes plugin images; `pb clean` empties pb's stores;
`pb lsp` serves an editor. `pb <verb> --help` has each one's flags,
and `docs/specs/` the contracts they keep.
